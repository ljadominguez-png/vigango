# F3.1: Google sign-in support in the database

**Date:** November 3, 2026
**Developer:** Bryan Balallo (Database)
**Branch:** committed directly to `Dev`
**Commit:** `e7220ee` (`Allow Google sign-in: nullable password_hash, add google_id`)
**Status:** Database and model changes completed and tested. Google login endpoint not implemented yet.

## Overview

ViganGo supports two ways to sign up and log in: email and password, and Google. The original `users` table required a password hash for every account, so a Google user, who has no password, could not be saved. This change makes the table and the `User` model support both methods.

## What changed

| Item                  | Before          | After                                                                                                    |
| --------------------- | --------------- | -------------------------------------------------------------------------------------------------------- |
| `users.password_hash` | `text NOT NULL` | `text`, nullable. It is empty for Google-only accounts.                                                  |
| `users.google_id`     | did not exist   | New `text` column, unique. Holds Google's stable user ID.                                                |
| Login-method rule     | none            | Check constraint `users_login_method_check`: every account must have a `password_hash` or a `google_id`. |

SQL applied to the Supabase database:

```sql
alter table public.users alter column password_hash drop not null;
alter table public.users add column google_id text unique;
alter table public.users add constraint users_login_method_check
  check (password_hash is not null or google_id is not null);
```

The `users` table was empty when this was applied, so no data was affected.

## Model change

File: `backend/app/models/user.py`

```python
__table_args__ = (
    CheckConstraint(
        "password_hash is not null or google_id is not null",
        name="users_login_method_check",
    ),
)
password_hash: Mapped[str | None] = mapped_column(Text)  # None for Google-only accounts
google_id: Mapped[str | None] = mapped_column(Text, unique=True)  # Google's stable user ID
```

The `Favorite` model and every other model are unchanged.

## How accounts work now

| Sign-up method     | `password_hash`   | `google_id` |
| ------------------ | ----------------- | ----------- |
| Email and password | set (argon2 hash) | empty       |
| Google             | empty             | set         |

`email` and `username` stay required and unique for both methods.

## For the backend

- **Login code must handle an empts `password_hash`.** A Google-only account that tries email and password login has no hash to check. `verify_password` or the login route must reject it cleanly and never crash.
- **Never return `password_hash` or `google_id` in an API response.** `UserResponse` should keep exposing only `id`, `username`, `email` and `image_url`.
- **Registration (F4.2) is unaffected.** It still sets `password_hash`.
- **A Google login endpoint is needed.** It should verify the ID token the Flutter app receives from Google, then find the user by `google_id` (or create one) and sign them in.

## Verification

- **Local tests:** `python -m pytest -v` passed all 10 tests against a disposable PostgreSQL container, with the new model.
- **Supabase:** the schema view shows `password_hash` as nullable and `google_id` as unique. A query on `pg_constraint` returns `users_login_method_check`.
- **Not tested:** creating a real Google account. That needs the login endpoint.

## Open decisions for the team

1. **Account linking.** If someone registers with email and later signs in with Google using the same email, should both methods use one account? Suggested: yes, link them by email.
2. **Usernames for Google users.** The `username` column is required, but Google does not provide one. Generate it from the person's name, or ask them to choose one.
3. **Case-sensitive email and username.** `Traveler@x.com` and `traveler@x.com` are currently different accounts. Suggested fix: unique indexes on `lower(email)` and `lower(username)`, and lowercase the email in the endpoint. Not applied yet.
