# F3.2: Case-insensitive unique username and email

**Date:** November 5, 2026
**Developer:** Bryan Balallo (Database)
**Branch:** `feat/f3.2-case-insensitive-users`
**Requested by:** Bello (F4.2 registration and Google sign-in)
**Status:** Tested locally. Not yet applied to Supabase.

## Problem

The `users` table had unique constraints on `username` and `email`, but they are case-sensitive. PostgreSQL treated `Traveler123` and `traveler123` as different usernames, while the backend now treats them as duplicates. Without a database rule, two requests arriving at the same time could both pass the backend's duplicate check.

## What changed

| Item | Change |
|---|---|
| `users_username_lower_idx` | New unique index on `lower(username)`. |
| `users_email_lower_idx` | New unique index on `lower(email)`. |
| Existing constraints | Unchanged. `users_username_key` and `users_email_key` stay in place. |

The backend's existing `IntegrityError` handling turns a violation of these indexes into HTTP 409.

## SQL for Supabase

Run in Supabase, SQL Editor, New query. Run the three parts in order.

**1. Pre-check.** Both `dup_groups` values must be `0`. If not, stop and resolve the duplicates first.

```sql
select 'username' as col, count(*) as dup_groups
from (select lower(username) from public.users group by 1 having count(*) > 1) u
union all
select 'email', count(*)
from (select lower(email) from public.users group by 1 having count(*) > 1) e;
```

**2. Create the indexes.**

```sql
create unique index if not exists users_username_lower_idx on public.users (lower(username));
create unique index if not exists users_email_lower_idx on public.users (lower(email));
```

This uses plain `CREATE INDEX`, not `CONCURRENTLY`. The `users` table had 0 rows when checked on November 5, 2026, so the lock is very brief. If the table grows large before this is applied, reconsider.

**3. Verify.** Both new index names must appear.

```sql
select indexname, indexdef from pg_indexes
where schemaname = 'public' and tablename = 'users';
```

**Rollback (only if needed):**

```sql
drop index if exists public.users_username_lower_idx;
drop index if exists public.users_email_lower_idx;
```

## Model change

File: `backend/app/models/user.py`

```python
# Case-insensitive uniqueness for username and email.
Index("users_username_lower_idx", func.lower(User.username), unique=True)
Index("users_email_lower_idx", func.lower(User.email), unique=True)
```

These lines come after the `User` class. Tables created from the model, such as the test fixture's `users` table, get both indexes automatically.

## Verification

Done locally against a disposable `postgres:17` container:

- The SQLAlchemy model generates `CREATE UNIQUE INDEX users_username_lower_idx ON users (lower(username))` and the matching email index.
- The full schema, with the two indexes added, runs on an empty database without errors and creates both indexes.
- Inserting `Traveler123` then `traveler123` fails with `users_username_lower_idx`.
- Inserting `Traveler@Example.com` then `traveler@example.com` fails with `users_email_lower_idx`.
- The SQL above, run on a database without the indexes, shows 0 duplicates, creates both indexes, and lists them.
- `python -m pytest -v`: 10 passed on this branch.

Supabase check before applying (November 5, 2026): no case-insensitive indexes existed; 0 duplicate groups for username and email.

**Not tested:** the live Supabase run, and Bello's 32-test suite on `feat/f4.2-google-signin-support` with this model change.

## Notes

- **Existing test databases:** the test fixture creates the `users` table from the model only if it does not exist. A test container that already has the table will not get the new indexes automatically. Recreate the container, or run part 2 of the SQL above against it.
- **Schema file:** `vigango-supabase-schema.sql` is not in the repo. Anyone keeping a local copy should add the two `create unique index` lines from part 2.
