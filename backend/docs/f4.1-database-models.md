## Overview

F4 added SQLAlchemy models corresponding to tables created by the team's Supabase SQL schema. The models describe existing database tables; they are not a substitute for the schema-creation SQL scripts.

A **model class** represents a table, its **mapped attributes** represent columns, and each model instance represents a row. Relationships let the application navigate related objects without constructing joins manually in each feature.

## Models and tables

| Model or association | Table             | Purpose                                                                                                        |
| -------------------- | ----------------- | -------------------------------------------------------------------------------------------------------------- |
| `Category`           | `categories`      | Tourism categories such as Heritage, Food, Culture, Recreation, Events, Local Products, Nature, and Nightlife. |
| `Area`               | `areas`           | Towns and areas in Metro Vigan.                                                                                |
| `Listing`            | `listings`        | Activities, sites, events, and products with details and location.                                             |
| `ListingImage`       | `listing_images`  | Images and listing-cover designation.                                                                          |
| `OperatingHour`      | `operating_hours` | Weekly operating schedules.                                                                                    |
| `EventSchedule`      | `event_schedules` | Date-based events and recurring schedules.                                                                     |
| `Tag`                | `tags`            | Searchable activity keywords.                                                                                  |
| `listing_tags`       | `listing_tags`    | Many-to-many association between listings and tags.                                                            |
| `User`               | `users`           | Account username, email, password hash, and optional image URL.                                                |
| `Favorite`           | `favorites`       | One saved listing per user/listing pair.                                                                       |
| `ListingStats`       | `listing_stats`   | Favorite counters maintained by database triggers.                                                             |

## Relationships

- A category and an area can each have many listings.
- A listing can have multiple images, operating-hour records, and event schedules.
- Listings and tags have a many-to-many relationship.
- A user can have many favorites; a listing can appear in many favorites.
- A listing has one statistics row with a favorite count.

Example relationships:

```python
listing.category.name
listing.area.name
listing.images
listing.tags
user.favorites
```

## Important design decisions

- All models share `Base` from `app/database.py`.
- Column types align with PostgreSQL, including exact `Numeric(10, 2)` fee values and time-zone-aware timestamps.
- Constraints and defaults mirror the team's SQL schema where applicable.
- Favorites are unique per `(user_id, listing_id)`; relevant deletes cascade through related records.
- Database triggers maintain favorite counts and the listing statistics row.
- User passwords are stored as hashes rather than plaintext and must never appear in API responses.
- The original report states the `users` and `favorites` tables have row-level security enabled without public API access policies. The FastAPI backend is responsible for authorized database access.
- The original schema also includes sign-up triggers; confirm their behavior with the database owner before changing registration workflows.

## Verification recorded in the original report

A `check_models.py` script loaded categories and a listing with its category and area through the live Supabase database. This verified that the model relationships could be read through SQLAlchemy.

Example from the original implementation:

```python
from sqlalchemy import select
from app.database import SessionLocal
from app.models import Listing

with SessionLocal() as db:
    featured = db.scalars(
        select(Listing).where(Listing.is_featured == True)
    ).all()
    for listing in featured:
        print(listing.title, listing.category.name)
```
