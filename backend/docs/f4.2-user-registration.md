## Goal

Allow new users to create ViganGo accounts through the FastAPI backend while validating input, checking duplicate credentials, and storing passwords securely. Registration reuses the existing [F4.1 database models](f4.1-database-models.md).

## API contract

`POST /api/v1/auth/register`

Example request:

```json
{
  "username": "traveler123",
  "email": "traveler@example.com",
  "password": "ExamplePassword123!"
}
```

Expected result: HTTP **201 Created** with a user response containing `id`, `username`, `email`, and optional `image_url`. No plaintext password or password hash is returned.

| HTTP status | Meaning                                                             |
| ----------- | ------------------------------------------------------------------- |
| `201`       | Registration succeeded.                                             |
| `409`       | Username or email already registered.                               |
| `422`       | Invalid input (for example, malformed email or password too short). |

## Implementation

| File, relative to `backend/` | Responsibility                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------ |
| `app/schemas/auth.py`        | `RegisterRequest` validates username, email, and password; `UserResponse` limits exposed fields. |
| `app/services/password.py`   | `hash_password()` and `verify_password()` using `pwdlib` and Argon2id.                           |
| `app/routers/auth.py`        | Defines the register endpoint, duplicate check, user creation, and conflict handling.            |
| `app/main.py`                | Includes the authentication router.                                                              |
| `app/models/user.py`         | Existing teammate-owned SQLAlchemy user model, reused unchanged.                                 |
| `app/database.py`            | Existing teammate-owned `get_db()` database dependency, reused unchanged.                        |

Registration flow:

1. Pydantic checks request data (`username`: 3–50 characters; `email`: valid address; `password`: at least 12 characters).
2. The router checks whether the username or email already exists.
3. The password is converted to an Argon2id hash.
4. SQLAlchemy adds and commits the `User` row to PostgreSQL.
5. Database uniqueness conflicts trigger a rollback and HTTP 409.
6. The API returns a `UserResponse` without exposing `password_hash`.

The router uses `Annotated[Session, Depends(get_db)]` for FastAPI dependency injection without a function-call default-argument lint warning.

## Google Sign-In Enhancement

### Overview

Extended F4.2 to support Google-backed accounts alongside traditional email/password registration.

The updated User model supports two authentication methods:

- Email/password accounts store an Argon2id password hash.
- Google-only accounts store Google's stable user identifier (`google_id`) and have a null password hash.

At least one authentication method is required.

### Google Registration Endpoint

`POST /api/v1/auth/google`

| Response | Meaning                                           |
| -------- | ------------------------------------------------- |
| 201      | New Google account created                        |
| 200      | Existing Google account found                     |
| 401      | Invalid Google identity token                     |
| 409      | Email or username conflict                        |
| 422      | New user missing a valid username                 |
| 503      | Google verification unavailable or not configured |

The endpoint does not issue an application access token.

### Security

- Google ID tokens are verified using `google-auth`.
- The verified `sub` claim identifies the Google user.
- Unverified email claims are rejected.
- Existing email/password accounts are not automatically linked.
- Password hashes and Google IDs are excluded from public user responses.
- Database integrity conflicts trigger transaction rollback.

### Implementation Files

- `app/services/google_identity.py` - Google token verification.
- `app/services/google_config.py` - OAuth client ID configuration.
- `app/schemas/auth.py` - Google request validation.
- `app/routers/auth.py` - Google registration endpoint.
- `tests/test_google_identity.py` - Token verification tests.

### Isolated PostgreSQL setup

From `backend/`, create the disposable local database if it is not already running:

```bash
docker run --name vigango-f42-postgres \
  --rm -d \
  -e POSTGRES_USER=vigango_test \
  -e POSTGRES_PASSWORD=local_only_password \
  -e POSTGRES_DB=vigango_test \
  -p 127.0.0.1:55432:5432 \
  postgres:17
```

Check readiness:

```bash
docker exec vigango-f42-postgres \
  pg_isready -U vigango_test -d vigango_test
```

Run the combined suite:

```bash
TEST_DATABASE_URL='postgresql+psycopg://vigango_test:local_only_password@127.0.0.1:55432/vigango_test' \
python -m pytest -v
```

The test fixture validates the local database target, creates the needed user table if absent, and uses an outer transaction with savepoints so successful registration commits can be tested and test-created user rows rolled back. The test container is independent of the team's Supabase instance.

To stop and remove the disposable container after testing:

```bash
docker stop vigango-f42-postgres
```

**Safety:** Never use production or team Supabase credentials in `TEST_DATABASE_URL`; do not commit `.env`. `docker stop` deletes this `--rm` container and its unpersisted data.

## Known limits and next work

- Current uniqueness checking is based on the model's database constraints; normalization and case-insensitive username/email rules need a team decision.
- Authentication login, JWT/session tokens, protected endpoints, and rate limiting are outside registration's current scope.
- Integration testing has covered local PostgreSQL, not the live Supabase registration workflow.
- Before merging the Google Sign-In enhancement: run all 30 tests together, review staged changes for secrets and unrelated files, push the enhancement branch, and open a pull request targeting Dev.
