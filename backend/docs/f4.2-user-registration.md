## Goal

Allow new users to register for ViganGo using email/password or a verified Google identity. Validate input, prevent duplicate accounts, hash local passwords securely, and persist accounts in PostgreSQL. Registration depends on the existing [F4.1 models](f4.1-database-models.md), the [F3.1 Google account fields](f3.1-google-sign-in-database.md), and the [F3.2 case-insensitive indexes](f3.2-case-insensitive-users.md).

## API contracts

### Email/password registration

`POST /api/v1/auth/register`

Example request:

```json
{
  "username": "traveler123",
  "email": "traveler@example.com",
  "password": "ExamplePassword123!"
}
```

Pydantic validates a 3–50-character username, email format, and password of at least 12 characters. The password is stored as an Argon2id hash, not as plaintext.

| HTTP status | Meaning                                                        |
| ----------- | -------------------------------------------------------------- |
| `201`       | New account created.                                           |
| `409`       | Username or email already registered, including case variants. |
| `422`       | Invalid registration input.                                    |

### Google account registration/retrieval

`POST /api/v1/auth/google`

Example request for a new Google-backed account (placeholder only; never commit a real token):

```json
{
  "id_token": "GOOGLE_ID_TOKEN_PLACEHOLDER",
  "username": "traveler123"
}
```

For a returning Google user, `username` may be omitted. The endpoint identifies the user by the verified Google `sub` claim, not by treating an email address as a stable Google ID.

| HTTP status | Meaning                                                                 |
| ----------- | ----------------------------------------------------------------------- |
| `201`       | New Google-backed account created.                                      |
| `200`       | Existing Google-backed account retrieved.                               |
| `401`       | Google identity token is invalid or rejected.                           |
| `409`       | Existing email, username, or database uniqueness conflict.              |
| `422`       | Invalid request or new user without a valid username.                   |
| `503`       | Google OAuth client ID missing or verification temporarily unavailable. |

Both routes return `UserResponse` (`id`, `username`, `email`, optional `image_url`). Neither returns `password_hash`, `google_id`, or an application access token. **This is account registration/retrieval, not a completed login or JWT/session flow.**

### Email/password flow

1. Pydantic validates the request.
2. SQLAlchemy checks usernames and emails with `lower(...)` to reject case-variant duplicates.
3. The plaintext password is hashed with Argon2id.
4. A new `User` is inserted and committed to PostgreSQL.
5. Uniqueness violations cause rollback and HTTP 409.
6. Only approved `UserResponse` fields are returned.

Both authentication routes use FastAPI dependency injection with `Annotated[Session, Depends(get_db)]`.

### Google flow

1. Require `GOOGLE_CLIENT_ID`; otherwise respond with HTTP 503.
2. Pass the ID token and expected audience to `google.auth`'s `verify_oauth2_token()`.
3. Reject invalid tokens or missing/unverified identity claims; transport failures are reported separately.
4. Look up an existing account by Google's stable `sub` identifier (`google_id`). Return HTTP 200 if found.
5. For new accounts, reject matching existing emails (no automatic linking), require a username, and check username conflicts.
6. Insert a user with `google_id` set and `password_hash=None`, then return HTTP 201.
7. Handle database integrity conflicts with rollback and HTTP 409.

## Database integration: F3.1 and F3.2

The [F3.1 database update](f3.1-google-sign-in-database.md) permits Google-only accounts with a null password hash. The model requires at least one login method (`password_hash` or `google_id`).

The [F3.2 update](f3.2-case-insensitive-users.md) adds SQLAlchemy unique indexes on `lower(username)` and `lower(email)`:

```python
Index("users_username_lower_idx", func.lower(User.username), unique=True)
Index("users_email_lower_idx", func.lower(User.email), unique=True)
```

These protect against case-variant duplicates at the database level, including races where two requests pass the API's preliminary duplicate checks. Existing case-sensitive unique indexes remain in place.

F3.2's teammate-authored report states that the equivalent indexes were applied and verified on the shared Supabase database on November 5, 2026. This report records that teammate verification; it is not a separate live Supabase test performed by F4.2.

We also verified locally that a **fresh PostgreSQL 17 test table created from the merged SQLAlchemy model** includes these indexes. Direct insertion of `Traveler123` and `traveler123` raised the expected uniqueness violation. The local test container is independent of Supabase.

**Fresh versus existing databases:** Creating a new table from the updated SQLAlchemy model generates the indexes. Calling `User.__table__.create(checkfirst=True)` against an existing table does not migrate it. Pre-existing databases must receive the reviewed index SQL separately; consult F3.2's documented pre-check and rollout steps.

## Security verification and limitations

- Google ID tokens are validated using `google-auth`, with the configured OAuth client ID supplied as the expected audience. Standard signature, issuer, and expiration checks are delegated to that library.
- The verified `sub` identifies the Google account. Empty Google IDs and emails are rejected.
- `email_verified` is accepted only as boolean `True` or the exact string `"true"`; missing, false, and `"false"` values are rejected.
- Invalid tokens return HTTP 401; unavailable Google verification or missing configuration returns HTTP 503.
- Existing email/password accounts are **not** automatically linked to Google identities with matching emails.
- Public user responses do not include password hashes or Google IDs.
- The Google verification tests mock the verification library. They test application handling of valid/invalid claims, wrong-audience/expired/issuer error paths, and transport failures. They **do not independently prove live Google OAuth verification or JWT cryptography**.
- Login sessions, JWT access tokens, account linking, rate limiting, and a live Google OAuth end-to-end check are **not included** in this F4.2 registration enhancement.

### Isolated PostgreSQL test setup

Create the disposable local test database if it is not already running (from `backend/`):

```bash
docker run --name vigango-f42-postgres \
  --rm -d \
  -e POSTGRES_USER=vigango_test \
  -e POSTGRES_PASSWORD=local_only_password \
  -e POSTGRES_DB=vigango_test \
  -p 127.0.0.1:55432:5432 \
  postgres:17
```

Check readiness:

```bash
docker exec vigango-f42-postgres \
  pg_isready -U vigango_test -d vigango_test
```

Activate the virtual environment and run the full suite with the local test URL:

```bash
source .venv/bin/activate
TEST_DATABASE_URL='postgresql+psycopg://vigango_test:local_only_password@127.0.0.1:55432/vigango_test' \
python -m pytest -v -ra
```

The test fixture validates the local target and uses an outer transaction plus savepoints for rollback of test-created rows. Do not point `TEST_DATABASE_URL` at production or team Supabase. The Google token verifier is mocked in automated tests, so no live Google credentials are required.

Stop the disposable container when finished:

```bash
docker stop vigango-f42-postgres
```

The container was created with `--rm` and no persistent volume, so stopping it deletes its stored test data. Recheck the safety of the Docker target before cleanup.
